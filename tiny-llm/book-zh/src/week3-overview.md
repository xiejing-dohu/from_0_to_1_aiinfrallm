# 🚧 第 3 周：构建 Mini vLLM

>                 本概述和载有同一标记的章节正在审查中
> 可能改变。

第3周将优化的单项请求模式变为多项请求服务
发动机。 学生增加排程,请求拥有缓存状态,共享页面池,
以及直接读取非相干 K/V 所需的运行时间元数据。 决赛
模型使用一个有页意识的注意界面,并有单独的列表用于
单键 decode 和多键 prefill.


## 我们将覆盖什么

- 连续批量和请求重复使用
- 断了 prefill 和排程器公平性
- 网页KV存储和页面行走注意
- 页面 FlashAttention 长久 prefill
- 可倒置缓存的可选投机解码
- 可选的专家混合模型支持

第1天 独立请求状态。 第二天
拆分长的预填表,使其不能垄断调度器。 第3天替换a
使用固定大小的缓存增长密度,同时保留密度加太
兼容路径 。 第4天,通过教人注意 来清除那些聚集起来的
页表直接带有正确的第一排表。 第5天,然后是瓷砖
同样的页面行走操作 与周2的矩阵碎片。 页翻译
因此,在加以优化之前先采用。

这五天是你们解决的必经之路 最终型号在
您的解决方案运行于页面 FlashAttention 长久 prefill 和页式矢量
用于简短查询的内核 。
两个时间表通过同一个块表界面读取同一个页池;
既不重建密集的K/V。

注意不是一种自动的单项请求暂时胜出。 检查
微量测量降低KV储存、页面再利用、增量增长和分批;
页面表间接可以让一个请求更慢。 它没有规定
没有内存封存的扫描, 接收能力提高。 每章结尾为:
重点计量,而
[业绩附录](./appendix-performance.md) 记录匹配的
逐章结果。

因拒绝而按页码解码
需要精确的缓存倒转操作,多键验证需要
页面意识长清路. MoE 独立于缓存和调度器,所以
它仍然是可选模式的扩展,不需要完成第3周。
