## 基准方法

前进者在新的过程中启动每个检查站,
换个顺序, 做完全要求的热身, 同步懒惰
MLX 在计时器内工作,并报告中位数:

```bash
pdm run bench-week2-progression --offline --repeats 4 --cooldown-seconds 1 \
  --model qwen3-4b --input-len 128 --output-len 129 --warmup 2 \
  --prefill-logits last --json-output week2-128.json

pdm run bench-serving-progression --offline --repeats 4 \
  --model qwen3-4b --num-seqs 16 --batch-size 4 \
  --min-input-len 128 --max-input-len 1024 \
  --min-output-len 32 --max-output-len 128 \
  --prefill-step 128 --warmup 1 --cooldown-seconds 1 \
  --json-output benchmark_results/m4-pro-qwen3-4b-week3-serving-mlx-0.32.0.json
```

`--prefill-logits last` 是一个供一代人使用的工作量:
解决方案和 MLX 仅将最后一个快速行输入词汇日志。 使用
`--prefill-logits all` 用于快速计分,但从不比较两种模式。
Decode 吞吐量不包括第一个生成的 token 因为... token 这是
生产 prefill.

MLX已发表 `mlx_lm.benchmark` 表格使用2,048个token提示和128个
生成的符号 。 这使得2K/128成为有用的静态图书馆比较点,
而不是寻呼接受测试或长文本证明。 使用上下文扫描 :

| 点 | 目的 |
|---:|---|
| 128 | 第2周 接收和简短互动请求 |
| 2,048 | 标准 MLX 型静态应力比较 |
| 8,192 | KV- 缓冲应力 |
| 16,384 | 8K路径后的压力点是健康的 |

`llama-bench` 通常使用即时处理 512 和符号生成 128 by
默认,这是又一次提醒,基准长度是惯例,而不是
普遍工作量。 总是发布准确的即时和输出长度.

下面的机器是一款20分的苹果M4 Pro GPU 和 64 GB 数据
记忆 静态周2排使用两个完整的热身和中位数4
平衡的新流程; 连续服务行使用一个热身和
四个平衡的新工艺的中位数。

|---|---|---|---|---|---|

| RoPE | 每个批次行一个有效偏移;甚至旋转尺寸;保留尾值 | 没有中间图的引信角生成和对旋转 | 保留用于 Qwen decode 行; 人头计算和旋转分配变化需要重新测量 | Python `mlx.core` RoPE 和仅可选择的RMSNorm检查站 | 将缓存或预计算角度路径与新角度构造比对基准 |
| 瑞士 | 门和上角的形状一样 dtype | Fuse SiLU 和门/上级产品成一个元素发送器 | 保留用于 Qwen MLP 形状; 微小的减震器和其他定型不是履约索赔 | 那个 Python `mlx.core` SILU产品和 RoPE 检查站仍可选择 | 接受操作员在不重复的完整模型收益的情况下获胜 |

| SIMD 矩阵 prefill | W4/组128布局, BF16 存储, FP32 瓦片堆积,并校正部分瓦片 | 复用激活和分量重的瓦片横跨快速行 | 所需路径 `M > 8`;部分和新的模型形状既需要正确性,也需要时间扫描 | 那个 Python `mlx.core` matmul 是正确性的预言; 第3天 Matvec 仍然是短排发送和香草 Metal 是一个带程控制 | 比较全记录课程 prefill 最后记录 MLX 服务 |

这是留存分类账,不是可移植性证书。 一个新的 GPU, MLX
释放,模型形状, dtype,或工作量重开相应行。

## 第4周的长期预算

上下文长度有单独的模型,内存,和耐久限制. 对于课程
Quen3-4B检查站,1个 token 页:1 BF16 K/V 状态

```text
36 layers * 2 (K and V) * 8 KV heads * 128 values * 2 bytes
    = 147,456 bytes = 144 KiB per token
```

检查站宣布 `max_position_embeddings = 65,536`,但其
`rope_scaling` 字段为空。 Qwen 文档 Qwen3 培训范围
[32,768个令牌](https://github.com/QwenLM/Qwen3/blob/main/docs/source/deployment/vllm.md#context-length)
和建议 RoPE 扩大规模,以便大大延长投入。 未修改的
因此,课程模型具有32,768个token的验证极限,尽管其具有以下特性:
配置允许进行更大的位置实验.

内存不是测量到的64GB M4 Pro的绑定限制. MLX 报告a
51.84 GiB 建议 GPU 工作组和量化检查站
1.99 GiB保留 8 GiB 启动、分配器松动和输出

```text
floor((51.84 GiB - 1.99 GiB - 8 GiB) / 144 KiB) = 304,738 tokens
```

估计是能力计算,不能超过模型
训练范围。 课程限制是最低限度:

```text
min(32,768 trained, 65,536 configured, 304,738 memory) = 32,768 tokens
```

第4周使用32,768个总代币作为硬背景预算. 开始
在输入之前压缩超过24 576个令牌,保留8 192个
用于下一个模型响应和大型工具结果的符号。 标记器必须
计算完整的请求,包括系统指令和工具
计谋.

### 慢到30万会怎样

FlashAttention 删除四进制分数矩阵分配; 不
将工作移走。 充分注意 prefill 上下文长度为四进制,
300K包含大约84倍于32K的注意力工作. 单键 decode
必须在每一层读取线性增长的 K/V 历史。

以下合成操作员扫描使用 MLX 0.32.0,一个Quen3-4B形
BF16 decode 查询, 三个新进程, 以及15个同步的中位数
每个进程发送。 最后一栏总结了隔绝的层层间隙
36层,是一个乐观的只注意的上限;一个完整的模型必须
还运行预测、正常化、取样和缓存更新。

| 背景情况 | 完整型号 BF16 KV 车次 | MLX 每层SDPA | 仅注意 decode 上限 |
|---:|---:|---:|---:|
| 2,048 | 0.28 GiB | 0.14 ms | 195.33 tok/s |
| 8,192 | 1.12 GiB | 0.29 ms | 96.72 tok/s |
| 32,768 | 4.50 GiB | 0.92 ms | 30.28 tok/s |
| 65,536 | 9.00 GiB | 1.73 ms | 16.08 tok/s |
| 131,072 | 18.00 GiB | 3.65 ms | 7.61 tok/s |
| 300,000 | 41.20 GiB | 9.49 ms | 2.93 tok/s |

300K运算器分配在 M4 Pro 上运行, 但从端到端的 300K 运行
课程检查站将超出其配置和培训范围,
会留下很少的工作室, 并且会做初始 prefill
不切实际。 作为内核应力测试是有用的,不是辅助课程
上下文。

MLX 包含多个长文本优化。 其引信GQA decode 路径
自动切换为上下文分隔的双通道还原;
[0.30.4 发布](https://github.com/ml-explore/mlx/releases/tag/v0.30.4)
特别叫出更快的长文本向量 GQA。 多语种关注
MLX-LM 快速评估以约束临时
启动 MLX-LM 也提供快速前置重用,一个旋转的固定大小
缓存,并量化 KV 存储 。 前缀再利用有助于重复的提示;缓存
旋转改变全心全意语义;和 KV 定量交易
精确度,有时是能力速度。 没有第一个是满300K
prefill 线性时间。

重用操作员扫描 :

```bash

  --json-output benchmark_results/m4-pro-qwen3-4b-long-context-mlx-0.32.0.json
```

### 第1天: 缓存前缀

密集的缓存使 prefill 一次性费用,但每次 decode 预测
仍读稠重. 因此,第1天从可敬开始 prefill 和
仅24.63 decode tok/s。结果给第2天提供了真实的缓存基线
计量。
